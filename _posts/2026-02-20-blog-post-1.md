## Why I Built a Personal Website

As someone working at the intersection of MR physics, signal processing, and system-level imaging engineering, I have come to realize that this is a truly multidisciplinary field, requiring knowledge from multiple domains. I therefore wanted a clean and structured way to present my work, both to communicate it clearly to others and to better organize and consolidate my own knowledge framework.

At this stage, I wasn’t looking for a flashy design or a blogging platform. What I wanted was:
- A website integrated with GitHub, with proper version control
- Full ownership of the content and structure
- Minimal external dependencies
- A clean, professional, and technical appearance


After some comparison, I chose [Academic Pages](https://academicpages.github.io), a Jekyll-based template built for GitHub Pages. This post summarizes the process, from setup to customization, including the pitfalls I encountered and the design decisions I made.


## Step 1 — Fork and Configure GitHub Pages

Fork the Academic Pages repository to your GitHub account, and rename the repository to:

```
username.github.io
```

This enables automatic hosting at:

```
https://username.github.io
```


Then, edit `_config.yml`. This is the global configuration file that defines the core properties of your website, such as the site title, theme, collections, author information, and permalink structure. First, modify the following fields:

```yaml
title: "Your Name"
description: "MRI Sequence & Reconstruction Engineer"
url: "https://username.github.io"
baseurl: ""
repository: "username/username.github.io"
```

Important:

- `url` must match your GitHub Pages domain.
- Restart Jekyll after modifying `_config.yml`.


## Step 2 — Local Development Setup (Mac)

[Ruby](https://www.ruby-lang.org/en/) is an interpreted object-oriented language used mainly for web development, and Jekyll is a static site generator written in Ruby, on which this template is based. In mac, ruby is part of the operating system. However, it is better to avoid using the built-in ruby, as it will have file permission issue. By using `sudo`, gem (package in ruby, for example, jekyll and bundler are gems, the command to install the packages are `gem install ...`) will be made in the default environment, which can interfere with the system. Thus, it would be better to install ruby manually and add it into the path.

As far as I tested, Ruby 4.x causes Liquid compatibility errors (`bigdecimal`, `csv` issues), which can be solved by manually adding these packages in Gemfile. However, to solve it in a more efficient way, it would be better to install ruby 3.x:

```bash
brew install rbenv ruby-build
echo 'eval "$(rbenv init - zsh)"' >> ~/.zshrc
source ~/.zshrc

rbenv install 3.3.6
rbenv global 3.3.6
rbenv rehash
```

Verify:

```bash
ruby -v
```

`node` is the environment for javascript, which is in parallel to ruby. I am not sure why this is needed, yet in the original github, this is suggested to be installed, which might be due to that some specific themes have used javascript.
```
brew install node
```

`bundler` is a dependency of ruby, which will read the Gemfile, install all necessary gems, generate the Gemfile.lock file and make sure that the versions are aligned:
```
gem install bundler
```


Then, install all the dependencies designated in the Gemfile. Inside your repository:

```bash
bundle config set --local path 'vendor/bundle'
rm -rf vendor/bundle .bundle Gemfile.lock
bundle install
```

To generate the local html and serve it from `localhost:4000`, run:

```bash
bundle exec jekyll serve
```

You can access the local website by:

```
http://localhost:4000
```



## Step 3 — Customed changes

To better reflect my experience and personal preferences, I made several modifications to the website layout. For example, I removed the Talks tab.
This was achieved by modifying the `navigation.yml` and `_config.yml` file. Also, I integrated conference presentations into the Publications section, and  implemented a small feature that allows each entry to redirect directly to the publication or conference website when clicked. This required modifying the page layout in `publications.html`and updating the relevant entries in the `./_publications/` collection accordingly.

To make the structure clearer, I generated an overview of the repository’s folder structure with explanatory comments below, making it easier to identify which files need to be modified to implement a specific feature. As a starting point, I have bolded the folders and files that I modified. Now it’s time to explore and experiment with the template freely.

**Folder structure:**  
.  
├── **_config.yml**  # Global configuration (title, name, author info, etc)  
├── _config_docker.yml  # Supplementary configuration file to `_config.yml` when running in a docker  
├── **_drafts/**  # folder to store the draft of the posts which will not be shown in the website  
├── **_includes/**  # reusable components, such as footer or header  
├── _layouts/  # page skeleton templates, eg., single page layout  
├── **_pages/**  # static tab pages, eg., publication tab and its layout   
├── _portfolio/  # project portfolio items  
├── **_posts/**  # blog posts  
├── **_publications/**  # publication entries, treated as a collection  
├── _talks/  # talks and conference presentations, not used in my case   
├── **_teaching/**  # teaching activities  
├── _sass/  # SCSS styling files for controls and theme  
├── _site/  # compiled static html output  
├── assets/  # CSSm HSm fonts, etc  
├── **files/**  # PDF files, eg., CV  
├── **images/**  # images    
├── **data/**  # to store the structured database, for example navigation.yml for tab setting     
├── talkmap/  # geographic visualization for talks, not used yet in my case  
├── markdown_generator/  # helper scripts for generating markdown  
├── scripts/  # utility scripts for custom automation  
├── .github/  # generated files when deployed by github pages  
├── .devcontainer/  # VS Code Dev Containers configurations for reproducible development environment across machines.
├── vendor/  # local ruby gems  
├── .bundle/  # local configuration and cache of bundler
├── .sass-cache/  # cache for CSS compilation  
├── Dockerfile  # containerized build environment  
├── docker-compose.yml  # docker orchestration  
├── Gemfile  # ruby dependencies  
├── Gemfile.lock  # locked dependency versions. 
├── package.json  # JS dependencies  
└── LICENSE  


## Closing Thoughts

Building this website was less about HTML and more about positioning. AcademicPages provides a solid structure, but it requires intentional refinement to reflect a specific profile and personal aesthetic.  

For me, the current goal was not to create a standard, professor-style academic page, but rather a personalized, technically grounded, and maintainable site that documents my work and development, one that evolves over time. Fortunately, this template provides a powerful yet accessible starting point.
